# Issue #14 — fontes de usage dos harnesses

Pesquisa em 22 de outubro de 2026. Escopo: percentuais consumidos dos limites de plano e horários de renovação, como na imagem da issue. **Uso da janela de contexto, custo da conversa, atividade de tokens e orçamento de API são medidas diferentes.** A análise abaixo usa documentação e código publicados pelos próprios projetos. Nenhuma integração foi testada com credenciais reais nesta pesquisa.

| Harness | Fonte para limites do plano | Percentual e reset | Condição principal |
| --- | --- | --- | --- |
| Claude Code | JSON entregue ao comando configurado como `statusLine` | 5 h e 7 dias (`used_percentage`, `resets_at`) | Pro/Max claude.ai; push a partir de uma sessão Claude ativa |
| Codex CLI | App Server JSON-RPC `account/rateLimits/read` | Janelas de cada bucket (`usedPercent`, `windowDurationMins`, `resetsAt`) | Conta ChatGPT; processo App Server independente pode consultar a conta |
| OpenCode | Para **OpenCode Go**, rota `/zen/go/v1/usage` encontrada no código oficial | 5 h, semanal e mensal (`percent`, `resetsAt`) | Chave Go; rota ausente da API pública documentada; outros providers não cobertos |

## Claude Code

A [documentação oficial da status line](https://code.claude.com/docs/en/statusline) define o mecanismo: Claude Code envia um JSON da sessão por stdin ao comando configurado em `statusLine`, cuja stdout vira a linha exibida no próprio Claude. O JSON contém `session_id`, diretório do workspace, `rate_limits.five_hour.used_percentage`, `rate_limits.seven_day.used_percentage` e os respectivos `resets_at` em segundos Unix. O `session_id` é estável ao longo da sessão. A documentação informa que `rate_limits` só aparece em claude.ai Pro/Max ou em gateway Claude com limite de gasto, depois da primeira resposta de API. Uma janela pode estar ausente. O comando roda no início da sessão e em eventos; pode receber `refreshInterval`, mas a ausência de mensagens durante ociosidade pode deixar a amostra antiga. [Campos, condições e exemplo oficial](https://code.claude.com/docs/en/statusline#rate-limit-usage).

Para uma TUI externa, a possibilidade comprovada é um **bridge opt-in**: um comando de status line registra localmente só os campos necessários com `session_id`, workspace e instante da amostra; a TUI lê a amostra e marca expiração. Isso é uma inferência arquitetural a partir do mecanismo documentado, não uma API de polling oficial. A configuração atual do usuário pode já ter uma status line; a solução teria de preservá-la e não tomar seu lugar inadvertidamente. O `session_id` evita misturar múltiplas sessões Claude, mas a TUI ainda precisa de uma regra explícita para escolher qual sessão do mesmo workspace mostrar. O comando interativo [`/usage`](https://code.claude.com/docs/en/commands) mostra os limites ao usuário dentro do Claude Code; a documentação não o apresenta como saída estruturada consumível por outro processo.

## Codex CLI

O [App Server oficial](https://developers.openai.com/codex/app-server) documenta o método JSON-RPC `account/rateLimits/read` para os limites ChatGPT. A resposta contém `rateLimits` e, quando há vários buckets, `rateLimitsByLimitId`; cada janela pode trazer `usedPercent`, `windowDurationMins` e `resetsAt` (Unix seconds). `account/rateLimits/updated` comunica atualizações. O código público define esses campos como opcionais onde aplicável e explicita que percentuais/reset não provam sozinhos permissão de uso; há `ordinaryUsageAllowed` opcional. [Protocolo tipado](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/src/protocol/v2/account.rs), [exemplo e notas dos campos](https://developers.openai.com/codex/app-server#6-rate-limits-chatgpt).

Uma TUI externa pode iniciar `codex app-server` em stdio e fazer o handshake `initialize`/`initialized` antes de ler os limites. O próprio guia descreve esse transporte como JSONL e o App Server como interface para clientes integrados; o comando/transporte está marcado experimental para produção. A chamada de leitura não aparece listada entre os métodos que exigem `experimentalApi`. Não é preciso iniciar uma conversa para lê-la, mas isso deve ser confirmado num spike com a versão instalada e uma conta ChatGPT. O App Server usa a autenticação configurada no Codex. A documentação atual permite que aplicações locais ou open source continuem usando a autenticação do App Server, mas recomenda migração para *Sign in with ChatGPT*; diz que seu uso em serviços comerciais ou hospedados nunca foi permitido. [Transporte, handshake e autenticação](https://developers.openai.com/codex/app-server).

O quota do Codex é de **conta/bucket**, não da thread ativa. Portanto, para exibir limites não é necessário identificar a thread que está no outro painel; para rotular a tela como “harness atual” ainda é necessário selecionar ou obter um vínculo confiável. A resposta pode ter buckets adicionais, e `primary`/`secondary` não devem ser rotulados como “5 h”/“semana” sem ler `windowDurationMins`. [`account/usage/read`](https://developers.openai.com/codex/app-server#7-token-usage-chatgpt) é outra métrica: atividade de tokens e agregados diários, não o saldo das janelas de plano. Os [limites da OpenAI API](https://developers.openai.com/api/docs/guides/rate-limits) também são outra métrica, de organização/projeto, não o uso da assinatura ChatGPT no Codex.

## OpenCode

O [OpenCode aceita muitos providers](https://dev.opencode.ai/v2/docs/providers), inclusive locais. Por isso não existe um “limite de assinatura do OpenCode” universal. O [servidor local documentado](https://dev.opencode.ai/v2/docs/api) expõe providers conectados, sessões, status, mensagens e eventos; não documenta uma rota para quota de plano de cada provider. O comando [`opencode stats`](https://dev.opencode.ai/v2/docs/cli/commands/) mostra atividade local de tokens e custo das sessões, e não o percentual restante de uma assinatura.

Há uma possibilidade específica para **OpenCode Go**: o [handler no repositório oficial](https://github.com/anomalyco/opencode/blob/dev/packages/console/app/src/routes/zen/go/v1/usage.ts) implementa `GET /zen/go/v1/usage` autenticado por chave Bearer Go e responde `usage.rolling`, `usage.weekly`, `usage.monthly`, cada um com `status`, `percent` e `resetsAt` em ISO 8601. A [documentação Go](https://opencode.ai/v2/docs/console/go) descreve as três janelas e diz que o consumo pode ser visto no Console. Porém a [API pública do Console](https://opencode.ai/v2/docs/console/api) lista inferência, providers e budgets, **não documenta essa rota de quota**. Logo a existência no código é evidência de viabilidade técnica, mas não de contrato estável. A documentação tampouco demonstra que a página web do Console usa essa mesma rota; não assumir isso. O uso de chaves locais exigiria consentimento e armazenamento seguro; não ler `auth.json` nem copiar credenciais silenciosamente. Outros providers teriam de ser avaliados um a um, pelas APIs próprias.

## Identificar “o harness em questão”

As três fontes medem algo associado a conta, chave ou sessão, não ao protocolo Relay. O campo `harness` do handoff indica quem o escreveu, e não qual processo está ativo agora. Várias sessões e até harnesses diferentes podem operar no mesmo workspace. A seleção manual (ou um vínculo explícito feito ao iniciar o painel) é mais verificável que inferência por último handoff, PID ou processo pai. Se nenhum vínculo existir, a tela deve dizer qual fonte/conta foi consultada e quando, sem afirmar “harness atual”. Claude exige ainda escolher entre amostras de sessões; Codex e OpenCode Go podem exibir limites de conta sem sessão ativa.

A [ADR-0003](../../docs/adr/0003-relay-tui-observador-de-terminal-em-rust.md) estabelece que `relay-tui` observa arquivos do workspace, **não lança processos**, não tem porta/token e mantém o core puro. Logo, a opção Codex via subprocesso `codex app-server` mudaria uma decisão arquitetural aceita e exigiria revisão explícita da ADR e do [design da TUI](../../app/relay-tui/DESIGN.md), antes de ser tratada como simples view. Conectar a um App Server já iniciado também introduz dependência de serviço/conexão que o painel atual não tem. Claude com bridge de status line e OpenCode Go por rede trazem fontes externas, idade de amostra, autenticação e falhas independentes do estado Relay. A alternativa de produto é uma vista opcional e separada de dados externos, com fonte escolhida pelo usuário e proveniência explícita.

**Avaliação:** a ideia é tecnicamente possível, mas a issue, como escrita, reúne três integrações distintas sob uma detecção automática que o Relay não consegue justificar. A utilidade adicional em relação aos comandos nativos (`/usage` no Claude Code, `/status` no Codex) é a consulta persistente no split sem interromper o trabalho; isso é uma hipótese de produto, não demonstrada pela pesquisa de APIs. Recomenda-se manter a issue como investigação até decidir se essa utilidade compensa ampliar a função atual do painel. Se avançar, especificar uma fonte por vez e fazer um experimento mínimo antes de mudar o design.

## Pontos para decidir antes de uma implementação

1. A issue pretende **limites da assinatura** (a imagem), ou também contexto, custo e atividade? Propor separar as métricas.
2. A TUI deve permitir escolher uma fonte explicitamente? “Detectar o harness atual” não tem uma evidência comum aos três.
3. Vale aceitar uma primeira versão Codex (API pública documentada), Claude com bridge opt-in, e OpenCode Go como pesquisa/spike devido à rota não documentada? A ordem pode seguir o harness mais usado, mas cada conector exige um contrato distinto.
4. Definir estado `indisponível` e idade da amostra quando faltar assinatura, credencial, primeira resposta, sessão vinculada ou rede. Não converter ausência de dados em `0%`.
5. Nenhum dado de usage deve modificar registros Relay ou o estado de integridade do protocolo. A vista seria observação externa e opcional.

## Experimentos mínimos sugeridos

- Codex: consultar `account/rateLimits/read` por stdio em uma conta ChatGPT já configurada; comparar com `/status`, registrar campos nulos, buckets e tempo da leitura, sem persistir credenciais.
- Claude: em ambiente descartável, acrescentar um comando de status line que faça bridge preservando uma status line preexistente; verificar amostras, reset, saída da sessão e duas sessões simultâneas.
- OpenCode Go: somente com chave fornecida voluntariamente para o experimento, confirmar se `/zen/go/v1/usage` responde com o esquema do código e como se comporta com a versão/conta atuais; não considerar isto contrato público até documentação ou garantia equivalente.
